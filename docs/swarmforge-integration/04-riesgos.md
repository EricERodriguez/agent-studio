# Registro de riesgos

Riesgos identificados durante la auditoría de la v1 del plan (lectura de código real +
subagente Software Architect independiente). Los primeros tres ya estaban implícitos en la v1;
el resto son adicionales, detectados en esta pasada.

| Riesgo | Detalle | Mitigación propuesta |
|---|---|---|
| Sin `LICENSE` en SwarmForge | Bloquea forkear/modificar el core o redistribuirlo dentro de la extensión | Modalidad `external` únicamente; adapter y wrapper son código propio de Agent Studio, no derivados |
| Agente se salta el wrapper de HIL/AIL | Invocando el script real por ruta absoluta o editando su propio `PATH` | Documentar como limitación conocida en la UI; no usarlo como único control para handoffs verdaderamente críticos (branch protection en el repo real como capa adicional) |
| Race entre el daemon y el interceptor | Si el agente puede escribir directo al `outbox` real sin pasar por el wrapper, el daemon lo entrega igual sin que el wrapper se entere | Mismo mecanismo de mitigación que el punto anterior — es la misma clase de riesgo |
| Sesiones tmux huérfanas tras crash de VS Code | tmux sobrevive al cierre de VS Code por diseño, pero si el proceso `handoffd.bb` o el propio swarm mueren mientras VS Code está cerrado, la reconciliación al reabrir puede no detectarlo | Diseñar explícitamente el chequeo de "¿el socket tmux sigue vivo?" al reabrir, como parte de la Fase 9 (no cerrado todavía, ver `PROGRESS.md`) |
| Portabilidad entre sistemas operativos | SwarmForge requiere zsh, tmux, Babashka; scripts documentados con supuestos de Bash 3.2 en macOS vs Bash moderno en Linux | Fijar el shell/versión mínima soportada explícitamente en el preflight (Fase 11) antes de lanzar un run; no asumir portabilidad sin probar en cada SO objetivo |
| Costo/consumo de las CLIs de agentes en paralelo | Correr un six-pack lanza 6 procesos de `codex`/`claude`/etc. simultáneos, sin límite de concurrencia ni estimación de costo previo en el plan original | Agregar un paso de preflight que muestre una estimación aproximada de "N agentes van a correr en paralelo" y permita al usuario confirmar antes de lanzar, especialmente para six-pack |
| Socket Unix sin autenticación adicional | El socket de `02-arquitectura-terminal-adapter.md` y `03-arquitectura-handoff-control.md` sólo se protege por permisos de filesystem (0700, mismo usuario) | Aceptable para un socket same-user en una máquina de desarrollo local; documentar explícitamente que este diseño asume que no hay otros usuarios no confiables en la misma máquina — no es un diseño válido para un escenario multiusuario o de servidor compartido |
| Falta de pin de commit al bajar packs | Bajar `two-pack`/`four-pack`/`six-pack` por tarball de rama sin fijar un commit puede traer cambios incompatibles sin aviso | El catálogo de templates de Agent Studio debe versionar el commit exacto usado para construir cada template (ya estaba en la v1 como buena práctica general, pero no explícitamente atado al mecanismo real de descarga por rama) |
| Confusión de marca con token cripto | El README de SwarmForge trae una advertencia en rojo sobre no gastar dinero en un "bankrbot SWARM token" — sugiere confusión/scam con un token cripto de nombre similar circulando | No es un riesgo técnico bloqueante; agregar una nota/disclaimer en la documentación de Agent Studio para que ningún usuario confunda ambos proyectos |
| Falta de smoke test de contrato real | Todo el diseño de `02` y `03` se basa en leer el README de SwarmForge, no en ejecutarlo de punta a punta con un adapter real funcionando | Antes de dar por buena la arquitectura, correr un swarm real con un `terminal-adapters/vscode.sh` mínimo (aunque sea un stub que abra `xterm` o similar) para confirmar que el contrato documentado se comporta como está escrito |
| Secretos dentro de `.agent-studio/runs/` | El directorio de configuración generado por run podría terminar conteniendo tokens de API u otra información sensible si un role prompt o constitution article los incluye por error | Agregar `.agent-studio/runs/` al `.gitignore` por defecto del proyecto del usuario (si no está ya) y documentar explícitamente que ese directorio no debe commitearse; considerar un chequeo de preflight que escanee patrones comunes de secretos antes de lanzar un run |
